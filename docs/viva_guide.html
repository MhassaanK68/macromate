STAGE 1 OF 10

What are we building?

Imagine taking the same chicken biryani photo through the program. We will follow it from the picture you see to the numbers the program changes.

What should the program tell us?

We want to give the program this photograph and receive suggested food names. It should put the best-matching name first. It can choose from eight names: chicken biryani, chicken pulao, chicken karahi, daal, nihari, haleem, samosa and chapati.

Choosing from a fixed list of categories is called classification. Each category is a class. The program stores these names in a Python list. Because Python starts counting at zero, chicken biryani has ID 0, chicken pulao has ID 1, and chapati has ID 7. An ID is a position in the list, not a quantity of food.

These four lines define the eight names in their fixed order. Later, a calculated score at position 0 must still mean chicken biryani.

The project is called Macromate. Its implemented result is the food ranking. A future meal logger would let a person confirm the food and enter its weight in grams. The current recognizer does not weigh this plate, work out its ingredients, or calculate its calories from the photograph. The screen and daily meal log are future work.

Our teaching rule: this is a real photo, but the tiny arrays and small calculations below are deliberately invented. They illustrate what operations mean. They are not measurements of what CLIP calculated for this photo. We reach the saved experiment results in stage 8. No model prediction or training is being run for this guide.

STAGE 2 OF 10

What does a photograph become?

Before discussing learning, look at the input. A program cannot calculate directly with “rice” or “chicken.” It needs numbers.

What is actually inside the picture?

When the image is opened, the picture is decoded into a grid of tiny positions. Each position has a color. One position is a pixel. A color photo normally describes each pixel with three numbers: how much red, green and blue. This is shortened to RGB.

In the image representation used here, each color number is an integer from 0 to 255. For example, [120, 80, 40] means red 120, green 80 and blue 40. It describes one color, not three separate pixels. The program receives these color numbers, rather than a word saying “rice” at that position.

Paper arithmetic · invented numbers

Pretend our biryani photograph contains only two rows and two columns. Each bracketed triple describes one pixel:

row 0:  [120, 80, 40]   [200, 160, 90]
row 1:  [ 90, 60, 30]   [240, 220, 180]

There are 4 pixels, each with 3 color numbers: 4 × 3 = 12 numbers altogether.

A rectangular collection of numbers like this is an array. You can think of its storage as regularly arranged Python lists, although the project uses libraries that store and calculate with the numbers efficiently. NumPy is the Python library used to turn the decoded picture into an array.

Image.open(path) opens the image file. The with statement makes sure it is closed afterward. Inside this block, the program can read its decoded colors.

Check your understandingHow many color numbers would a 2-row, 3-column RGB picture contain?

2 × 3 × 3 = 18 numbers. The first two factors count pixel positions; the final factor counts red, green and blue at each position.

Why do people write a picture’s shape as several numbers?

The array’s shape tells us how its numbers are arranged. Our tiny picture starts with shape [2, 2, 3]: 2 rows, 2 columns, 3 colors at each position. A color component is also called a channel.

The project rearranges these numbers so all red values form one grid, all green values another, and all blue values another. For our tiny picture, the red grid is [[120, 200], [90, 240]]. This rearranges positions; it does not recolor the photo. The new shape is [3, 2, 2]: channels first, then rows, then columns.

The project later uses pictures with 224 rows and 224 columns. One such picture has shape [3, 224, 224]. The 3 still means colors. It does not mean three photographs.

Calculations will also use fractions. Dividing a color by 255 changes its range from 0…255 to 0…1; our red value 120 becomes 120/255 ≈ 0.4706. Numbers stored in a format supporting these fractional calculations are called floating-point numbers. The project uses the format called float32.

np.array(...) copies the colors into a NumPy array, and dtype=np.float32 selects that numerical storage format.

transpose(2, 0, 1) moves the old color direction, numbered 2, to the front. / 255.0 performs the rescaling we just calculated.

The project also uses PyTorch, a Python library that can do these array calculations and later help calculate how the program’s stored numbers should change. A PyTorch array is called a tensor. For now, read “tensor” as “an array of numbers,” rather than as something mysterious.

The image-calculating code expects a collection of pictures, even when that collection contains only our one picture. Adding this outer collection changes [3, 224, 224] into [1, 3, 224, 224]. Read it slowly: 1 photo, 3 color grids, 224 rows, 224 columns. Eight pictures together would be [8, 3, 224, 224]. Each counted direction is called an axis; this arrangement has four axes.

Check your understandingDoes adding the leading 1 create another copy of our photograph?

No. It adds a way to say “this collection contains one photograph.” It changes the arrangement description from one image to a one-image collection, without duplicating its pixel values.

STAGE 3 OF 10

What is a model, and what can learning change?

We now have numbers representing the photograph. Next we need a calculation that turns those numbers into useful answers.

What is a model, if I think of it as a Python program?

A model is a calculation with stored numbers that control its behavior. Its input is our photograph’s numbers. Its output is another set of numbers that we can use to choose a food. The stored numbers inside that calculation are called weights. They are different from the pixel values: pixels describe this photograph; weights belong to the model and are reused for many photographs.

Paper arithmetic · invented numbers

For a deliberately tiny version, pretend our photo has already been reduced to the number 2. Let the calculation be:

photo_number = 2
weight = 0.2
output = photo_number * weight
       = 2 * 0.2
       = 0.4

The input 2 and weight 0.2 play different roles. A different weight would change the output even if we kept the photograph’s input unchanged. This one multiplication is a teaching model, not CLIP’s image calculation.

A real model combines many such weighted calculations. Macromate calculates eight raw output scores, one for each food name. A raw score before it is converted into a share of the eight choices is called a logit. You only need to recognize that word as the variable name for those scores.

PyTorch lets a model object be called like a function. One execution from input numbers to output scores is a forward calculation; it calculates an answer using the weights as they currently are.

This line sends a collection of image numbers, pixels, through model and stores its eight-per-photo scores in logits.

Check your understandingIf we keep the photo input 2 but change the weight from 0.2 to 0.3, what changes?

The output changes from 2 × 0.2 = 0.4 to 2 × 0.3 = 0.6. The photograph did not change; a stored number controlling the calculation changed.

What changes when we say the model “learns”?

Suppose our tiny calculator is supposed to output 1 for the biryani photo. We compare its current output with that desired answer. With weight 0.2, it outputs 0.4. With weight 0.3, it outputs 0.6, which is closer to 1. Changing a weight to make answers fit known examples better is the basic idea of learning. Running this weight-adjustment process is also called training.

The desired answer is a target. In the real project, the target is the correct food’s ID, such as 0 for chicken biryani. It is not a desired value for every pixel. The program keeps the photo’s input and target and changes selected weights inside the model.

This does not mean someone writes a rule such as “if rice is yellow, choose biryani.” The learning calculation uses examples to adjust the stored numbers. It also does not mean every proposed weight change is good. Stage 6 will show how the program chooses a direction for a change.

Source: models/train.py:90–102 · run_epoch()

Check your understandingDuring learning, does the program make the photograph look more like biryani?

No. It changes selected model weights. The input photograph and its assigned answer stay the same. The aim is for the model’s calculations to give a better answer for that input and, eventually, other similar photos.

STAGE 4 OF 10

What has CLIP already learned?

Our project starts with a model that already has learned weights. We need to understand what those earlier calculations make possible.

Do we have to teach the model how to see from nothing?

No. The project loads an existing model named CLIP. Before this project, CLIP was trained to associate photographs with accompanying text. That earlier work produced stored weights that can turn pictures and descriptions into comparable numerical summaries. Using weights learned earlier is called using a pretrained model.

Reusing that earlier learning for our food task is called transfer learning. We did not perform CLIP’s original training. We load its saved numbers and later adjust a selected part using our food examples. This can reuse useful earlier patterns; it does not guarantee that every Pakistani dish will be recognized correctly.

from_pretrained(...) reconstructs CLIP using saved weights. CHECKPOINT names CLIP and REVISION selects an exact saved version.

cache_dir points to local model files. local_files_only=True requires them to be present rather than downloading them. The remaining options select the weight-file format, a particular internal calculation method, and floating-point storage. The image model’s internal steps are optional in stage 8.

Check your understandingIf someone says “we trained CLIP from scratch,” does that describe this repository?

No. The repository loads pretrained CLIP. Its own food training changes only selected existing weights, which we will identify in stage 8.

How can a photograph be compared with words?

CLIP has one calculation for images and another for text. The image calculation takes the photograph’s many pixel numbers and produces a shorter list. The text calculation takes the description “a photo of Pakistani chicken biryani” and produces another list. These lists are not food names. They are numbers learned so matching pictures and descriptions tend to agree.

Such a numerical description is called a representation, or an embedding. The part of the model that makes it is called an encoder.

In our project, the final image and description lists each contain 512 numbers. A 512-number list is also called a 512-dimensional vector. “512” counts numbers in a description, not food categories. This is an internal summary, not yet the eight final food scores.

Paper arithmetic · invented numbers

On paper, replace each 512-number list with only two numbers. Let our biryani photo’s list be [3, 4]. Let the description for biryani have comparison list [1, 0], and the description for pulao have [0, 1]. These coordinates are made up. In the real model, coordinate 1 does not simply mean “rice,” and coordinate 2 does not mean “chicken.”

Before comparison, CLIP also applies a learned numerical conversion to each encoder’s summary. This conversion is a projection: multiplications and additions that put the image and text summaries into the matching 512-number format.

Paper arithmetic · invented numbers

Here is one way to make our [3, 4] comparison list from two invented working values [10, 10]:

first output  = 10 × 0.1 + 10 × 0.2 = 3
second output = 10 × 0.3 + 10 × 0.1 = 4
result = [3, 4]

The four multipliers are weights. Real CLIP uses larger learned conversions, but the computer still calculates each output from weighted input numbers.

Words must first become numbers too. A helper splits a description into stored text pieces and looks up an integer ID for each piece. These pieces are called tokens. Their IDs are inputs for the text encoder, not the eight food-class IDs. In the code, tokens contains this packaged numerical text input.

clip.text_model(**tokens) runs the text encoder. Here tokens contains the description in numerical form; ** passes its named entries as function arguments. .pooler_output selects one summary of the whole description.

text_projection(pooled) performs the learned conversion to the comparison format. These text descriptions are prepared once, rather than reread for each photograph.

Check your understandingWhy are equal-length lists not enough, by themselves, to compare an arbitrary image program with an arbitrary text program?

CLIP’s earlier training made its image and text calculations work together. Two unrelated programs could both output 512 numbers without those numbers having compatible meanings.

How do we compare our two-number lists?

First remove differences caused only by list length. The length of [3, 4] is the square root of 3² + 4², which is √25 = 5, because 5 × 5 = 25. Here 3² means 3 × 3. Divide both entries by 5: our photo becomes [0.6, 0.8]. Its length is now 1. This operation is called unit-length normalization.

Next multiply corresponding entries and add the results. For the biryani description [1, 0], calculate 0.6 × 1 + 0.8 × 0 = 0.6. For pulao [0, 1], calculate 0.6 × 0 + 0.8 × 1 = 0.8. Multiplying matching entries and summing is a dot product.

Because both lists have length 1, this dot product compares their directions rather than their overall size. That comparison is called cosine similarity. A larger value means a closer directional match. Our invented example currently prefers pulao, even though the real food is biryani. A model can be wrong.

Source: models/clip_classifier.py:23 · fixed text-list normalization; models/clip_classifier.py:44–45 · image normalization and comparison

Check your understandingWhy should [6, 8] give the same normalized direction as [3, 4]?

Its length is 10, so dividing [6, 8] by 10 also gives [0.6, 0.8]. Doubling the original list does not change its direction. Without normalization, its dot products would instead double.

STAGE 5 OF 10

How does our project choose a food?

We have the ingredients: a numerical image description, numerical food descriptions, and a way to compare them. Now connect them.

How does the program turn CLIP into an eight-food chooser?

The project writes one description for each food using the same wording: a photo of Pakistani followed by its name. A description supplied to a model is often called a prompt. Our eight prompts give eight numerical text lists, kept in class-ID order.

The loop adds the same phrase to each name. For ID 0, the result is a photo of Pakistani chicken biryani. It repeats for the seven other foods.

For our one photo, the model makes one 512-number image list. It compares this list with each of the eight 512-number text lists. This leaves eight similarities. It multiplies them by one positive number saved with pretrained CLIP, producing the eight logits. A positive multiplier changes their separation but not which is largest.

The image list has shape [1, 512]: one photo, 512 coordinates. The text lists have shape [8, 512]: eight descriptions, 512 coordinates each. Comparing every photo list with every description list gives [1, 8]. For eight photos together, it gives [8, 8]: photos along the first direction, foods along the second.

Line 43 runs the image encoder and takes its summary. Line 44 projects that summary and divides by its length, as we did with [3, 4].

Line 45 compares with all food descriptions. .T turns the text arrangement from [8, 512] into [512, 8]. @ performs all the multiply-and-add comparisons. logit_scale.exp() supplies a positive multiplier. The returned numbers are still raw scores.

Check your understandingDoes the 8 in [1, 8] mean eight color channels?

No. At this point pixels have already been converted into an image summary and compared with text. The output’s 8 positions now correspond to the eight food names, in their saved class-ID order.

Why does the output include scores between zero and one?

A raw score does not directly say how much of the total preference belongs to each food. The program converts all eight scores into positive shares that add to 1. Here is the literal calculation, using our same deliberately small example.

Paper arithmetic · invented numbers

Use an invented multiplier of 2. Biryani similarity 0.6 becomes logit 1.2; pulao similarity 0.8 becomes logit 1.6. For simple arithmetic, assign each of the other six foods a logit of 0.

biryani: exp(1.2) ≈ 3.320
pulao:   exp(1.6) ≈ 4.953
others:  exp(0) = 1 each
total:   3.320 + 4.953 + 6 × 1 ≈ 14.273

biryani share = 3.320 / 14.273 ≈ 0.2326
pulao share   = 4.953 / 14.273 ≈ 0.3470
each other share = 1 / 14.273 ≈ 0.0701

exp(x) means raise the fixed mathematical number e, about 2.718, to the power x. It turns a raw score into a positive number. Dividing by the same total makes the shares sum to 1.

This conversion is called softmax. It preserves which raw score was larger, so pulao still comes before biryani in our invented result. Putting names in score order is ranking.

At this point logits contains the eight scores for one photo. dim=0 says to convert along those eight food positions. It produces their shares, stored in scores.

These shares are not tested promises of correctness. The program must distribute a total of 1 among its eight choices even if the photograph shows an unfamiliar food. Checking whether, for example, predictions scored 0.8 are actually correct about 80% of the time would be a separate study. This repository does not establish that agreement; its output explicitly says the scores are uncalibrated.

Optional depthWhat happens if we increase the multiplier?

Keep our toy similarities unchanged and make their differences larger. Pulao remains first, but softmax can give it a larger share. The decision can therefore become more emphatic without becoming more correct. This is arithmetic on our invented scores, not a running model.

Check your understandingWould a score of 0.99 prove that this plate is biryani?

No. It would be a share of preference among these eight names under the model’s calculation. The scoring system has not been shown to make 0.99 mean 99% correctness, and it has no implemented unfamiliar-food rejection guarantee.

STAGE 6 OF 10

How does one learning step work?

Our invented scores put pulao first. We know the teaching photo is labelled biryani. How can the program use that disagreement to change a weight?

How does it measure how wrong the answer is?

A teaching example includes the photograph and its expected food name. That supplied name is the label. Here the label is chicken biryani, stored as ID 0. Learning with supplied answers is called supervised learning.

We need a number that becomes smaller as the model gives more preference to the correct food. That number is a loss. This project uses a loss called cross-entropy. For one photo it takes the correct food’s softmax share and calculates its negative natural logarithm: loss = −ln(correct_share).

You do not need to derive logarithms to read this code. ln is a mathematical operation, provided by Python as math.log. The important behavior is that a correct share near 1 gives a small penalty, and a share near 0 gives a large penalty. At 0.5 the penalty is about 0.693; at 0.1 it is about 2.303.

Paper arithmetic · invented numbers

For our current invented biryani share, the loss is −ln(0.2326) ≈ 1.4584. If the image’s direction changed from [0.6, 0.8] to [0.8, 0.6], swapping the first two toy scores, its biryani share would become 0.3470 and its loss would fall to about 1.0584. This illustrates an improvement; it is not a recorded weight update.

This constructs PyTorch’s cross-entropy calculator. nn is the project’s short name for PyTorch’s model-building tools.

The first line calculates the raw food scores. The second compares them with the supplied IDs. CrossEntropyLoss performs the needed logarithm/softmax calculation internally, so the training code passes raw logits, not scores already converted by softmax.

ID 0 selects which score counts as the answer. It does not mean that the biryani score should become zero. For eight photos together, the code calculates the mean of their losses: add the eight penalties and divide by eight. Such a group processed together is a batch.

Check your understandingIf the first-ranked food stays unchanged but the correct biryani share rises, can loss improve?

Yes. Cross-entropy responds to the correct food’s share, not only to which name is first. A loss improvement does not always immediately change the first-ranked food.

How does it know which way to change a weight?

Return to our one-weight calculator from stage 3: input 2, weight 0.2, output 0.4, desired output 1. To make the arithmetic visible, measure this calculator’s mistake as the squared gap: (output − 1)². This squared-gap loss is only for this teaching calculator; the project uses cross-entropy.

Paper arithmetic · invented numbers
weight 0.20 → output 0.40 → mistake (0.40 − 1)² = 0.3600
weight 0.21 → output 0.42 → mistake (0.42 − 1)² = 0.3364

weight change:    +0.01
mistake change:   −0.0236
change ratio:    −0.0236 / 0.01 = −2.36

The negative ratio tells us that a small increase in this weight reduces this mistake. The exact slope at weight 0.2 is −2.4. Such a slope is called a gradient. With many weights, there is one slope for each weight value.

A smaller trial change makes the ratio closer to that exact slope: weight 0.2001 gives output 0.4002 and mistake 0.35976004. The ratio is (0.35976004 − 0.36) / 0.0001 = −2.3996. These trials help us understand the direction; the real program obtains gradients from the known calculation rules instead.

PyTorch does not need to try every weight twice. It remembers the arithmetic used to make the output and works backward through it. For this tiny calculator, the squared mistake has slope 2 × (0.4 − 1) = −1.2 with respect to the output. The output 2 × weight changes twice as fast as the weight, so the weight’s slope is −1.2 × 2 = −2.4. Combining local slopes backward through the calculation is backpropagation.

Now choose how large a move to make. A learning rate controls that move. With an invented rate 0.05, a simple update is new_weight = old_weight − rate × gradient. That gives 0.2 − 0.05 × (−2.4) = 0.32. The new output is 2 × 0.32 = 0.64, and the mistake falls to (0.64 − 1)² = 0.1296.

A rule that turns gradients into weight changes is an optimizer. The real project uses a more elaborate rule called AdamW, introduced in stage 8. Its learning rates are also different from our invented 0.05.

loss.backward() works backward and calculates slopes for the weights allowed to learn. It does not yet change their values.

optimizer.step() uses those slopes to change the allowed weights. This is the actual update. Keeping these two lines distinct is essential.

Check your understandingIf the gradient is negative, why does subtracting it increase the weight?

Subtracting a negative number adds a positive number. In our example, 0.2 − 0.05 × (−2.4) = 0.32. That direction reduces this calculator’s current loss. It is a local direction, not a guarantee that arbitrarily large increases will always help.

What happens in one real training step?

The real step uses eight photos and their labels. Include our biryani photo as one of those teaching examples. Their input shape is [8, 3, 224, 224]; the model calculates [8, 8] raw scores. The label list has shape [8], one food ID per photo. The shared weights are used for all eight photos.

Before calculating this batch’s slopes, the program clears the previous batch’s stored slopes. Otherwise, PyTorch would add the new values to the old ones. After calculating the new slopes, the code limits an excessively large combined slope size, applies the optimizer, and prepares the next learning rate. The details of those two safeguards come in stage 8.

zero_grad(set_to_none=True) clears the previously stored gradients. The next two lines calculate fresh scores and a fresh loss. Then the backward() and step() lines we just read complete the update.

Check your understandingDoes each photo in the batch get its own separate model?

No. All eight use the same weights. Their losses are averaged and their combined information contributes to one shared update. At prediction time, the same model can instead receive just our one photo.

STAGE 7 OF 10

Which photos teach, and which photos check?

Learning from a photo is not the same as checking whether learning works. First make the inputs consistent, then give different photos different jobs.

Why can’t we give every picture to the model exactly as it arrives?

The pretrained image calculation expects a consistent input size and numerical format. Our repository photo is 432 × 432 pixels. The project makes its input 224 × 224. Applying these preparations before the model is called preprocessing.

The program first obeys any stored rotation instruction and converts the picture to RGB. It resizes the shorter side to 224 while keeping the current proportions. For our square photo, both sides become 224. The scale is 224/432 ≈ 0.5185. Where new pixel positions fall between old ones, nearby colors are combined to estimate them; the code selects the bicubic method for this resize.

Next it keeps a centered 224 × 224 area. If there were extra rows or columns after resizing, this would cut them off. Our square-to-square example has no extra area to remove. The provider had already supplied a square export, so this step cannot restore any proportions lost before collection.

Line 84 corrects orientation and creates RGB. Lines 85–88 calculate the resized dimensions, round them to whole pixels and perform the resize.

Lines 89–90 choose the centered area. // 2 means integer division by two: any remainder is discarded because pixel starting positions must be whole numbers.

We already divided colors by 255 in stage 2. The program then subtracts a fixed reference value from each color and divides by a fixed scale. These constants match CLIP’s input convention, rather than being calculated from our checking photos.

Paper arithmetic · invented numbers

Keep the same invented red pixel value 120 from our tiny biryani picture:

120 / 255                         ≈ 0.470588
0.470588 − 0.48145466             ≈ −0.010866
−0.010866 / 0.26862954            ≈ −0.04045

A negative result is allowed. It means this red value is below the fixed red reference, not that the image is broken.

This is pixel normalization. Unlike the unit-length normalization of a whole image summary in stage 4, it rescales each color value using fixed channel constants. The two operations have different jobs.

The first two lines arrange three constants, one per color, so each is reused across its entire color grid. The last line subtracts the matching mean, divides by the matching scale, and converts the NumPy array into a PyTorch tensor.

Prepared training images are saved as ordinary RGB PNG pictures. Loading them still performs division by 255 and pixel normalization, once. It does not repeat the resize/crop. New uploads use the full preparation route.

Source: data scripts/preprocess.py:37–47 · clip_preprocess(); models/data.py:77–94 · image_tensor()

Check your understandingShould we normalize an already normalized tensor again?

No. That would change its numerical meaning. Saved prepared PNGs have not yet had numerical normalization stored in them, so the model loader normalizes them once. Do not confuse a viewable PNG with the final normalized tensor.

Why don’t we let every photo change the weights?

The collection of labelled photographs is the dataset. This project has 400 photos, 50 per food. They are divided into three groups because we need to answer three different questions.

Training photos supply the examples used by backward() and optimizer.step(). Validation photos are checked without weight updates while we decide which version to keep. Test photos are reserved for the final measurement after those choices. Each food contributes 35 training, 8 validation and 7 test photos.

Our running photograph belongs to the training group in the saved split. We may use it to explain learning. The seven biryani test photos mentioned later are other photographs. We are not treating this one training image as proof of performance on unseen photos.

Source: data/processed/split.csv:68 · our photo → train; models/data.py:59–64 · required per-food counts

A complete pass through the training photos is an epoch. After each epoch, validation asks how well that version handles the checking photos. Fitting the teaching photos very closely without learning patterns that work on other photos is called overfitting. A perfect answer on a familiar biryani photograph does not establish reliable recognition of another plate.

The training dataset accepts only train and val. Asking it for test raises an error. The evaluator has its own test-photo reader. This protects the intended separation in the normal workflow.

Check your understandingWhy not choose the best epoch by checking the test photos after every epoch?

Then their answers would influence the choice of model, so they would become part of development. We would no longer have that same independent final check. Validation is used for choosing; the reserved test group is used for measuring afterward.

What if a smaller copy of our biryani photo lands in testing?

Suppose the training group contains our photo and the test group contains a resized copy of the same photo. A correct test answer could mean “recognizes a familiar photograph,” rather than “recognizes a new plate.” Information about a checking example has entered the teaching process. This is one kind of data leakage.

An identical or very similar copy is a duplicate. The code checks exact file copies using a calculated fingerprint called a hash: identical file bytes produce the same SHA-256 fingerprint. It also makes a much shorter description of neighboring brightness changes, called a difference hash, to flag some visually similar copies even when their file bytes differ.

Known related photos are grouped before splitting. The split assigns a whole group to one job. It uses seed 42 to make its shuffled choices repeatable for the same inputs. The saved summary reports no group crossing between jobs and no close-hash pair crossing them. That is evidence about these checks, not a guarantee that all possible shared origins have been found.

For a detected pair, these lines check that both images remain in the collection and join them into one group. The later assignment moves the group together.

Optional depthWhere did the photos come from, and what can cleaning miss?

The four source records are IndianFoodRecog / EnVisionAI (64 selected), combined-dataset / Rafias Workspace (258), Bangladeshi Food Classification2 / NSN (28), and samosa / new (50). The source classes were mapped to our eight names; for example, Bangladeshi morog polao is included within chicken pulao. That mapping broadens what the class covers.

Cleaning checks names, IDs, paths, readable image files and recorded fingerprints. Exact duplicates with the same label keep one copy; conflicting labels on identical bytes are excluded. Likely visual duplicates are flagged for review rather than silently removed. The brightness hash flags pairs differing in at most 6 of its 64 bits. It can miss related images, and a similar hash is not proof of the same meal.

The saved cleaning summary retains all 400 images, records zero exact/threshold-close duplicates, and retains four file-size outliers. Those outliers are unusual file sizes, not automatically wrong foods. All 400 labels still await a second human review. The recorded licenses are uploader statements; the original provider archives and READMEs are absent.

The saved grouping also has six multi-image groups. Some use generic names such as image_46 across different foods. A shared name can overgroup unrelated pictures; a different name can miss a genuine relationship. These rules reduce a risk without proving every photo is independent.

Check your understandingDoes “no duplicate found” mean the photos are certainly independent?

No. It means none was found under the chosen fingerprints and grouping information. A crop, another view of the same plate, a misleading name or an unknown shared source can escape those rules.

What did this project actually train and measure?

Which part of CLIP did we actually change?

The image calculation contains a sequence of processing sections, each with its own weights. Such sections are called layers; a repeated group of layers is called a block. This CLIP image encoder has 12 blocks. Most keep their pretrained weights unchanged.

Our project changes the last two blocks, the final internal rescaling layer, and the image projection that produces the comparison list. It keeps the earlier image sections, the text encoder, the text projection and the comparison multiplier unchanged. Weights kept unchanged are called frozen. Adapting selected pretrained weights using our labelled food photos is called fine-tuning.

The first loop sets the learning flag to false for all CLIP weights. requires_grad means whether PyTorch should track slopes for those weights.

The second loop enables slopes only for blocks 10 and 11, the final normalization layer and the projection. Numbering starts at zero, so blocks 10 and 11 are the last two of twelve.

The text comparison lists stay fixed too. Learning changes how our biryani picture is represented relative to those fixed descriptions. The recorded count is 14,570,496 trainable weight values. Keeping most weights fixed limits what can change; the files do not prove this exact choice is the best possible design.

Optional depthWhat happens inside the image encoder’s blocks?

Divide our 224 × 224 input into squares 32 pixels wide and 32 pixels high. There are 7 squares along each side, so 49 squares. Each is a patch. A learned calculation turns each patch’s 3 × 32 × 32 color numbers into 768 working numbers.

The model adds position information so it can distinguish, for example, the plate’s top from its bottom. It also adds one special working summary position. There are now 50 positions, each with 768 numbers: shape [1, 50, 768] for our one photo. The special position is often called a class token, but it does not already contain the food ID.

Inside a block, positions combine information from other positions. The model calculates how strongly each source position should contribute, then takes a weighted mixture of their numbers. This operation is called attention. For a toy pair of patch values 10 and 2, contribution weights 0.75 and 0.25 produce 0.75 × 10 + 0.25 × 2 = 8. Real positions carry lists, and the contribution weights are calculated from learned comparisons between those lists.

Several attention calculations operate in parallel, called heads. This image encoder has 12 heads. Each block also applies further weighted calculations with a nonlinear operation: a rule that cannot be reduced to one fixed multiplication-and-addition rule. Squaring a value is a simple example of a nonlinear rule, although it is not the particular rule CLIP uses.

The computer also adds earlier working values back to the corresponding newly calculated values. For one invented coordinate, an earlier value 2 plus a new contribution 3 gives 5. Such an addition is a residual connection, allowing earlier information to continue through the blocks.

The final summary position gives one 768-number list. The visual projection maps it to 512, and unit-length normalization prepares it for text comparison. This patch-based architecture is a Vision Transformer, or ViT. ViT-B/32 is the pretrained variant’s name; /32 indicates patch width. These are architecture-derived shapes, not new measured intermediate outputs for our photograph.

How does one update become the complete training run?

The real optimizer is AdamW. It uses recent gradients and their squared sizes to adjust weight steps, rather than applying only the simple rule from our one-weight calculator. It also gently shrinks eligible weights; this extra constraint is called weight decay. That changes weight values, not image pixels.

The two trainable image blocks use base learning rate 0.00002, written 2e-5 in Python. The final rescaling layer and projection use 0.00005, or 5e-5. The rates vary during training: initially increase them, then smoothly reduce them. A rule for that variation is a learning-rate schedule.

Each batch has 8 photos. One epoch uses 280/8 = 35 weight updates, followed by checking all 64 validation photos without updates. The maximum was set to 20 epochs. At the end of each epoch, the program asks first how many validation photos were correct, and only then uses lower validation loss to break a tie.

This returns two values: correct count, then negative loss. Python compares the first value first. Only equal counts make the second value relevant, and a smaller loss gives a larger negative-loss value.

The recorded epoch 5 got 59/64 validation photos correct with loss about 0.2099. Epoch 6 got 61/64 with loss about 0.2160. Epoch 6 wins because the correct count comes first, even though its loss is slightly higher.

After five epochs without improvement, training stops. This is early stopping, and five is its patience. The actual run completed 11 epochs: epoch 6 was best, then epochs 7–11 did not improve it. The exported weights are from epoch 6, not epoch 11. An exact count-and-loss tie keeps the earlier version.

Optional depthWhat do warmup, gradient clipping and the other settings mean?

The schedule is planned for 20 × 35 = 700 updates. Its first 10%, or 70 updates, form warmup: small starting learning rates increase toward the base rates. A smooth cosine-shaped reduction follows. Because the run stops after 11 epochs, it does not complete the entire 700-update schedule. The code advances the schedule after each batch update.

Before an update, the program measures the combined length of all trainable gradients and limits it to 1.0. This is gradient clipping. If that length were 5, multiplying all gradients by about 1/5 would keep their collective direction while reducing their size. The code also rejects invalid numerical values such as infinity. These are safeguards; no comparison here proves what performance would be without them.

AdamW uses weight decay 0.01 for eligible weight arrays, but none for biases or normalization parameters. A bias is an added learned offset; a normalization parameter adjusts internal scale or offset. Within the last two blocks these use the block rate, while the final normalization uses the projection rate. AdamW’s two averaging settings are 0.9 and 0.999, with a tiny denominator safeguard 1e-8.

Seed 42 controls the recorded random choices such as training-order shuffling. It supports repeatability with matching inputs and software; it does not promise identical arithmetic on every device. Dropout means temporarily suppressing selected internal contributions during training; the configured value is zero here. No random image augmentation is performed by the current training loader.

Six earlier two-epoch trials compared a few settings. The retained choice, block_high, had 58/64 validation correct and lower loss than the other candidates tied on count. The trial named baseline also fine-tuned weights; its name does not make it a zero-shot measurement. The full run then started from pretrained weights using the chosen settings, rather than continuing the trial’s weights. A short comparison on one small validation set does not establish universally optimal settings.

Optional depthWhat do precision, recall, F1 and ROC-AUC ask?

Stay with biryani. Among the 56 real test photos, 7 actually have the biryani label and 49 do not. All 7 were called biryani, and no other photo was called biryani. That gives 7 correct biryani calls, 0 incorrect biryani calls, and 0 missed biryani photos. These counts can be organized in a confusion matrix: rows are actual names; columns are suggested names.

Precision asks “of the photos called biryani, how many really were biryani?” Here it is 7/(7+0) = 1. Recall asks “of the real biryani photos, how many were found?” It is also 7/(7+0) = 1. A wrong call of biryani would lower precision; a missed biryani would lower recall.

F1 combines precision and recall using 2 × precision × recall / (precision + recall). With both equal to 1, biryani F1 is 1. The repository calculates each food’s F1 and takes the equal-weight average, called macro F1. Its saved value across all eight foods is about 0.9641. It is not the F1 of only our biryani category.

Another question compares the biryani score across different photos. Does a real biryani photo receive a higher biryani score than a non-biryani photo? There are 7 × 49 = 343 such pairs. All have the desired ordering in the saved biryani scores. A summary of this ranking behavior is the one-vs-rest ROC-AUC, which is 1.0 for biryani.

To see where its name comes from, imagine calling a photo biryani when its biryani score exceeds a chosen threshold. Lowering the threshold finds more true biryani photos but can admit more non-biryani photos. A ROC curve plots the fraction of non-biryani photos admitted horizontally against the fraction of biryani photos found vertically. AUC is the area under that curve; it also equals the pairwise ranking credit just described. Ties get half credit. If there are no biryani examples or no other-food examples, the area is undefined; the code returns null.

Across all eight categories, saved macro ROC-AUC is about 0.9985. A high AUC is not a guarantee that the first food choice is correct, nor a guarantee that a score is a reliable probability. It asks about one food’s scores across photos, whereas top-1 compares eight food scores within a photo.

The diagonal count tp is the correctly named food count. support counts actual examples of that food; predicted_count counts first suggestions of that food.

The next three lines divide these counts to compute precision, recall and F1. The conditional expressions choose zero when a denominator would be zero.

Can I explain the whole project without reciting a list of terms?

Macromate takes one food photograph and ranks eight supported food names. For our biryani photo, the computer first reads color numbers and prepares a consistent 224 × 224 input.

It uses pretrained CLIP to make a 512-number image description and compare it with eight fixed numerical text descriptions. Larger scaled similarities give higher-ranked foods. Softmax produces relative scores, which are not guaranteed confidence.

We adapt selected image-side weights using labelled training photos. Cross-entropy measures how much preference the correct food receives. Backpropagation calculates slopes and AdamW changes the allowed weights. Validation chooses the saved version; separate test photos measure it.

The recorded experiment used 280 training, 64 validation and 56 test photos. It selected epoch 6 and recorded 54 of 56 correct first choices. The collection is small, labels await another review, and a saved zero-shot baseline is missing. The intended calorie/serving workflow is not implemented. Current prepared-file fingerprint differences also limit exact reproduction of the historical run.

Practice questions

Attempt an answer aloud before opening it. The answers use the same running example and code route rather than introduce another project.

Check your understandingWhat is the difference between pixels and weights?

Pixels describe this biryani photograph’s colors. Weights are reusable stored numbers controlling the model’s calculation. Training changes selected weights, not the original photo.

Check your understandingWhat do [1, 3, 224, 224] and [1, 8] mean?

The first is one photo, three color grids, 224 rows and 224 columns. The second is one photo’s eight food scores after image/text comparison. Shape meanings depend on where the array appears.

Check your understandingWhy do we need a text encoder if our input is only a photograph?

The eight candidate names were converted to fixed text comparison lists earlier. Our new photo’s image list can then be compared with them without typing a new caption or rerunning the text encoder for each photo.

Check your understandingWhy normalize image and text descriptions?

With unit-length lists, the dot product compares direction. Our [3, 4] and [6, 8] both become [0.6, 0.8], so an arbitrary change in overall size does not double their similarity.

Check your understandingAre we training with CLIP’s original image/caption-matching objective?

No. That earlier paired-image/text learning produced pretrained CLIP. This repository uses a food photo’s supplied class ID and supervised cross-entropy across eight fixed food descriptions. The text encoder is frozen.

Check your understandingWhy pass logits rather than softmax shares to CrossEntropyLoss?

The PyTorch loss calculator performs its own numerically stable logarithm/softmax computation. Giving it already converted shares would make it apply the calculation to the wrong kind of input.

Check your understandingWhy is softmax dim=0 in predict(), but dim=1 in batch evaluation?

After selecting one photo, its score array has shape [8], and direction 0 contains the foods. A whole batch has shape [number of photos, 8], so direction 1 contains the foods. We convert each photo’s food scores together, not photos against each other.

Check your understandingDoes loss.backward() update weights?

No. It calculates gradients. optimizer.step() uses them to change the allowed weights. zero_grad() clears old gradients so batches do not unintentionally accumulate them.

Check your understandingWhat is frozen here?

Early image sections, the text side and comparison scale retain their pretrained weights. The last two image blocks, final image normalization and visual projection can learn. The eight text lists are fixed.

Check your understandingWhy are the text lists stored with the model as a buffer?

A buffer is fixed tensor data attached to the model, rather than an optimizer parameter. It can move with the model to the chosen device. The code detaches the text features from earlier gradient history and stores them with the checkpoint.

Check your understandingIs eval() the same as disabling gradients?

No. eval() selects layer behavior appropriate for prediction. inference_mode() or disabled grad tracking prevents backward bookkeeping for that call. requires_grad flags select the parameters whose slopes may be tracked. These controls have different jobs.

Check your understandingWhy does the final normalization use the projection learning rate?

make_optimizer() assigns the block rate only to names under vision_model.encoder.layers. Final post_layernorm is outside that prefix, so it receives projection_lr, while receiving no weight decay because it is normalization.

Check your understandingWhere should I point if asked to trace one prediction?

Recognizer.predict() in models/infer.py calls image_tensor() in models/data.py, then DishClassifier.forward() in models/clip_classifier.py. After the model returns logits, predict() performs softmax and stable ranking.

Check your understandingWhat breaks if food names are reordered but the stored scores are not?

Score position 0 would be described as a different food even though it was calculated against the biryani text list. Label order is part of the checkpoint and data checks, not cosmetic formatting.

Check your understandingWhat changes if we remove the projection?

The image encoder’s working summary has 768 numbers, whereas the text comparison lists have 512. The existing dot-product comparison would no longer fit. The projection is an existing learned CLIP conversion, not a newly added eight-food classifier layer.

Check your understandingWhat changes if we make the learning rate much larger?

Each slope can produce a much larger weight change, possibly overshooting a useful setting or damaging pretrained behavior. The repository does not provide evidence that arbitrarily larger rates improve this task.

Check your understandingWhat if we unfreeze the text encoder too?

The current forward uses saved detached text lists, so merely changing text parameter flags would not make that unused encoder receive a learning signal. Training it would require changing the computation, then a separately validated experiment.

Check your understandingCan a model improve its loss without improving top-1 accuracy?

Yes. It can give biryani a larger share without yet moving it above pulao. Loss sees that change; top-1 counts only the largest score. Conversely, a few very confident mistakes can worsen loss even when more first choices are correct.

Check your understandingWhy not use the same test photos to choose a better prompt after seeing their errors?

Those photos would then influence development choices. A new independent test set would be needed to support an unbiased final claim for the revised model.

Check your understandingCan the model reliably reject an unfamiliar meal?

That capability is not implemented or established. It still ranks eight offered foods. A largest softmax share is not proof that the true food is among them.

Check your understandingWhat is still missing scientifically?

Independent second label review, an unadapted CLIP baseline measurement, broader external Pakistani meals, stronger source-independent evaluation and validated score reliability. These are needed studies, not current results.

Check your understandingWhy should users confirm the food before nutrition is applied?

Recognition can be wrong. Even the correct food label does not identify the recipe or serving mass. The intended calculation is reference_per_100g × entered_grams / 100 after confirmation. For the recorded biryani reference, 106.89 kcal/100 g at 150 g would give 160.335 kcal for that reference recipe, not a direct measurement of our photo.
